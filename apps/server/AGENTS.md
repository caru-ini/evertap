# apps/server

Rules for the server and the CLI that the code does not show. Add a rule here only if it applies to `apps/server` alone, cannot be read from the code, and would be costly to get wrong.

- One binary: `src/main.ts` runs the server for `serve` and the CLI for every other command.
- Drivers throw `DataError` for what the person asked wrong and `UnavailableError` for what is not ready yet, such as a first download, and the router shows their messages. Anything else is an infrastructure failure, and the caller is sent to the Doctor.
- Every listener takes its address from the settings (`access.ts`) and moves when they change (`listenAt` in `live/listener.ts`, registered with `access.follow`), so a mode change needs no restart. Never bind a fixed address or `0.0.0.0` on your own.
- Each engine has one entry that listens in-process (`live/postgres-proxy.ts`, `live/redis-proxy.ts`, `live/tcp-forward.ts`, `live/s3-proxy.ts`) and routes to the right instance. Containers publish on 127.0.0.1 only. PostgreSQL and Redis run one instance per resource, routed by user, MySQL one per resource behind ProxySQL, and Garage one shared instance.
- A PostgreSQL resource's user is a superuser who can run programs in its instance, and a MySQL resource's user holds every privilege in its own. Those instances share one network whose containers cannot reach each other (`network: "isolated"`), never a network each: Docker's address pools hold about 30, shared with the person's Compose projects. PostgreSQL instances run under Docker's init, as PostgreSQL as process 1 restarts when a program it did not start exits.
- ProxySQL runs on the host's network, as nothing on the isolated one can reach an instance, and listens only on Unix sockets in a directory only evertap's user can enter: a port on 127.0.0.1 could be taken by anyone on the machine while ProxySQL is down, and evertap sends every MySQL password to its admin. Bun's MySQL client falls back to TCP when a socket is missing, so the admin client points that fallback at port 1. ProxySQL reaches each instance where Docker publishes it on 127.0.0.1, so evertap rewrites a route when Docker restarts an instance on a new port. Never share a volume between instances: they all run as the same user.
- evertap keeps no session in a PostgreSQL resource's own databases or `template1`: it measures and manages through `postgres`, and the data browser closes its session after each request. A session left there makes the app's `DROP DATABASE` and `CREATE DATABASE … TEMPLATE` fail.
- A bucket resource is a Garage key allowed to create buckets, and a first bucket under the key's local alias with read and write but not owner, since an owner could delete it while empty, past `protected`. Buckets the key creates are its own, under its local aliases. Never give a bucket a global alias, which takes the name from every other key, and never create a dedicated storage instance: local aliases already keep keys apart, and another Garage adds no feature.
- Buckets reached from anywhere share one more entry (`startPublicS3`) on a listener of its own, so where a request arrives, never its Host, tells it from the relay's. It answers only requests signed with a switched-on resource's key, since local aliases repeat bucket names across keys, and marks every answer `Cloudflare-CDN-Cache-Control: no-store`. Read the key exactly where and how Garage reads it (`signingKey`, `formKey`), refusing anything ambiguous: a request that names one key to evertap and another to Garage passes on the other key's signature.
- The S3 entry forwards requests unchanged, since SigV4 signs the Host, and records use per access key. It answers ACL requests from evertap's keys itself, since Garage has no ACLs, and gives each bucket a key creates the first bucket's open CORS rules before it answers.
- The data browser connects with the resource's own credentials, straight to its instance, so evertap's own reads and writes are not counted as use. The UI's uploads and downloads pass through evertap on the UI's origin: a browser sent to a bucket's endpoint fails from an HTTPS page or a phone.
- The Doctor sends paths, the Docker socket, and start errors only to callers on the local Unix socket (`context.local`). Network callers get the rest.
- A Cloudflare credential, an API token or access approved in Cloudflare (`cloudflare-oauth.ts`), lives only in the process that makes one change: the server's for Settings, setup's for `evertap setup`. Never store it, log it, or send it to a browser, and revoke approved access once the change is done. The settings keep only what runs the tunnel and the ids to remove it with. A person makes, moves, or removes a tunnel (`system.settings.tunnel`), from a signed-in browser or the local socket, never a paired CLI, an API key, or MCP.
- On its own, evertap reaches only Docker Hub (through Docker), GitHub's `releases/latest` once a day (`update-check.ts`), and Cloudflare for a tunnel it runs. `docs/security.md` promises that list and that nothing about the machine is sent, so change that page with any new outgoing request.
